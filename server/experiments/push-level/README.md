# 推关模拟实验（2026-09-04）

本轮证明了官方战斗核心可以在 Node 中独立运行，并已把它接入后台推关服务作为可选的“本地模拟加速”模式。该模式对服务器签发的战斗先做本地预测：失败局立即重新取局，胜利局保留并等待正常战斗时长后调用 `fight_level`。原有服务器计时模式保持不变。

## 已完成的验证

### 离线运行与一致性

加载版本匹配的 launcher、TEST_REMOTE_MODULE、game 中的必要模块及 8 份配置资源，跳过网页、登录和网络启动入口。2026-09-04 的运行时初始化得到 789 个配置导出项、43 个战斗类型。

当前资源版本：游戏代码 `2.44.2`，Cocos 引擎 `2.4.9`，battleVersion `7f91491b47`，配置提交 `79c4111dc4`。页面实际加载的资源短版本为 launcher `9706c`、TEST_REMOTE_MODULE `dfe5b`、game `3cf1d`、config `79c4111dc4`。`asset-lock.json` 固定每份资源的公开 URL 和 SHA-256，下载和运行前均核对。

游戏在 2026-09-04 更新后，第一份真实样本被旧锁中的配置提交 `4b48d8ffc9` 正确拒绝。刷新时发现公开通用入口仍可能返回前一版清单，因此版本更新必须以已登录页面实际加载的资源 URL 为准，不能只读取通用入口。随后锁定今天同一次页面加载中的代码、配置和战斗版本，再进行复算。

第二轮查验网页公开的 `cocos2d-js-min.a5841.js` 及客户端初始化代码后，修正了先前将游戏代码版本写入 `BattleConst.ENGINE_VERSION` 的错误。原 90 场测试只验证当时输入下的重复/倍速一致性；新版导出对照测试使用纠正后的引擎版本。

人工输入矩阵：第 100 关，英雄 101，5 组攻血数值 × 3 个种子 × 3 档 timeScale（1、100、1000）× 2 次重复，共 90 场。每场使用新建的战斗工厂及相同的战斗 ID，避免旧实例复用。

- 同组重复运行及不同 timeScale 的 `isWin`、`round`、`totalFrame`、`outputCode` 全部一致。
- 覆盖了判负、判胜、4 回合战斗。
- 第一次完整矩阵单场计算约 26–114 ms，整理后的再次运行约 26–115 ms。不含资源加载与工厂初始化。
- timeScale=1000 未优于 100。这里所有档位均直接推进模拟时间，timeScale=1 也没有等待真实时间；这不是与浏览器实时播放的耗时比较。
- 样本是人工单英雄输入，不能代替真实五将、宠物、武器和自动点击条件下的准确性验证。

### 网页短测

通过已登录的游戏和用户导入的原脚本，点击“推关模拟”，观察日志后点击“停止模拟”。

| 项目 | 观察结果 |
| --- | --- |
| 关卡 | 8700，Boss 畏尾鱼 |
| 启动时间 | 22:18:09（页面日志） |
| 停止时间 | 22:18:25（页面日志） |
| 判负次数 | 17 |
| 预测胜利 / 实际过关 | 0 / 0 |
| 最终状态 | 已停止，之后复查计数仍为 17 |

约 16 秒内出现 17 条判负并请求重置的记录，证明网页端可以反复提前放弃失败局。日志时间精度为秒，不能据此给出精确的单次延迟。

没有采集网络响应，所以还不知道每次请求是否改变种子、服务器限制以及各次重置请求的完成时间。没有胜利样本，不能验证胜利结算。尚未取得同一份真实输入在浏览器和 Node 中的配对结果。

另外，停止日志之后同一秒又出现了第 17 次失败日志。原脚本在 `await simulateMainPushBattle()` 返回后没有重新检查运行状态，存在停止时仍有一次模拟完成并请求重置的竞态。接入后台时需要使用任务代次或取消标记，禁止旧任务继续提交。

本轮遇到画布内“模拟”按钮不显示的问题，切换到装备页再返回战斗页后已出现；DOM 面板此前已经创建。加载时机是可能原因，尚未完成根因验证。

## 在项目根目录复现

使用 Node 22 或更新版本及项目已有的 TypeScript 开发依赖：

```powershell
node server/experiments/push-level/prepare-assets.mjs
node server/experiments/push-level/synthetic-probe.mjs
```

本地默认资源和结果位置为 `tmp/xki-analysis/`，此目录已被 Git 忽略。生产环境设置 `DATA_DIR` 时默认使用其下的 `battle-assets/`，也可通过 `XYZW_BATTLE_ASSETS` 显式指定其他目录。结果写入 `synthetic-results.json`。

`prepare-assets.mjs` 会复用校验通过的文件；缺少资源时从锁定的公开 URL 获取。旧版本 URL 若被撤回，需要重新分析并锁定同一套新版资源，不能混用配置和引擎。

`offline-runtime.mjs` 是实验加载器，尚未经过生产级生命周期、并发及内存验证；Node VM 也不应视为不可信代码的安全沙箱。

## 真实样本的导出与比较

实际操作发现：原脚本的诊断钩子主要采集塔、战斗 UI、回放等数据，主线模拟重试不会自动写入诊断列表。因此 v0.1 辅助脚本虽然已在网页正常显示，也提示“当前还没有诊断样本可导出”。

v0.2 增加“采集当前主线（单次）”和“下载主线样本”：复制当前主线 battleData、清空副本中的战斗结果和运行中缓存、保留种子及队伍，读取自动点击配置，使用新建的无画面战斗实例进行一次浏览器模拟。v0.3 还将结果写入页面中可见的只读“主线样本 JSON”文本框，供不支持 Blob 下载的侧边浏览器读取。v0.4 增加“服务器取局并模拟（单次）”，调用游戏自己的 `FightService.getLevelBattleData({})` 取得一局后立即模拟和导出，用来验证后台所需的协议路径。v0.5 增加可中止的“连续筛选（最多20局）”：每次判负后等待 300 ms 再取下一局，遇预测胜利立即停止并保留该局，达到上限或手动停止也不再取局。所有模式均不调用 `fight_level`，也不发出主线重置信号。若原脚本的加速推关仍在运行，要求先停止，避免其对自动点击的全局修改影响对照。

1. 在网页右上角雪花的脚本管理器里导入本目录最新的 `diagnostic-export.user.js`，保留原来的战斗模拟脚本。网页保存独立副本，本地修改后需要重新导入。
2. 返回战斗页，点击“采集当前主线（单次）”。等待提示“样本就绪”，再点击“下载主线样本”。
3. 将下载的 `xyzw-main-level-*.json` 放进 `tmp/xki-analysis/`。文件包含阵容及角色标识，保持在忽略目录中。
4. 在项目根目录运行：

```powershell
node server/experiments/push-level/compare-sample.mjs tmp/xki-analysis/xyzw-main-level-实际文件名.json
```

比较器先核对版本，然后在独立 Node 运行时还原 Map/Set 等结构，用 1 倍、100 倍各复算两次。比较胜负、回合、总帧数、输入码和输出码，结果写入忽略目录中的 `real-sample-comparison.json`。结果不一致或版本不匹配会返回非零退出码。

v0.5 已通过语法检查及 `export-roundtrip.test.mjs`：用真实引擎和人工队伍运行导出脚本，模拟下载 JSON，再交由另一运行时复算，4 次结果一致，并验证不会修改原输入、版本不匹配会被拒绝。记录为 `synthetic-export-comparison.json`，明确标记人工样本。

### 2026-09-04 真实账号配对结果

在第 8700 关采集两份不同随机种子的当前主线输入。浏览器各运行一次；独立 Node 运行时分别以 1 倍和 100 倍各复算两次。以下字段逐项完全相同：`isWin`、`round`、`totalFrame`、`inputCode`、`outputCode`。

| 样本 | 随机种子 | 结果 | 回合 | 总帧数 | 浏览器更新次数 | Node 1 倍更新次数 | Node 100 倍更新次数 |
| --- | ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 2801 | 失败 | 6 | 3933 | 63 | 6147 | 63 |
| 2 | 6665 | 失败 | 6 | 3734 | 60 | 5836 | 60 |

两份样本的总帧数和校验码不同，说明对照覆盖了不同战斗随机序列；每份样本的四次 Node 结果内部一致，并与浏览器结果完全一致。这证明今天版本下，真实账号的主线输入可以由独立 Node 战斗核心确定性复现。样本仍均为失败局，因此尚未证明预测胜利后的服务器结算流程。

### 服务器连续取局结果

v0.4 连续执行两次单次取局，随机种子从 `6158` 变为 `4754`；两局均为失败，且均通过独立 Node 的 1 倍、100 倍重复复算。由此确认 `fight_getlevelbattledata` 可以直接取得新的随机局，不需要先等待当前战斗结束或调用 `fight_startlevel`。

v0.5 随后执行一次最多 20 局的连续筛选：20 局均失败，20 个随机种子全部唯一，达到上限后自动停止，未调用 `fight_level`。服务器取局耗时为 49–69 ms，平均 54 ms；浏览器百倍速模拟耗时为 480–1012 ms，平均 585 ms。最后一局也通过独立 Node 复算。这个账号当前关卡未取得胜利样本，胜局保留及结算需要换用有一定过关概率的账号继续验证。

换用另一账号后，v0.5 在第 5894 关首局取得预测胜利；v0.6 在第 5895 关首局取得预测胜利。两份胜局都通过独立 Node 的 1 倍、100 倍重复复算。v0.6 保留第 5895 关胜局后立即调用 `fight_level`，服务器返回错误码 `200020`，说明服务器拒绝过早结算。该局的 1 倍模拟需要 17087 次、每次推进 20 ms，约等于 342 秒的正常战斗时长。

v0.7 在第 5898 关先调用页面战斗对象的 `PAUSE_BATTLE`，取得随机种子 7491 的预测胜局，并通过独立 Node 精确复算。等待期间页面仍自动推进到第 5899 关，证明暂停可见战斗对象不足以暂停网页内部的主线协议循环。网页会覆盖实验保留的服务器战斗，因此不能在同一页面可靠验证延迟后的胜局结算；后续结算实验必须使用独立后台 WebSocket 连接。

### 服务器直接取局结果

在同一已登录会话、同一第 8700 关连续两次调用游戏官方 `FightService.getLevelBattleData({})`，服务器均返回完整可模拟的 `battleData`，随机种子依次为 6158、4754，无需先调用 `fight_startlevel`。浏览器分别预测失败（8 回合、4613 帧）和失败（1 回合、6484 帧）；两份数据随后在独立 Node 中以 1 倍和 100 倍各复算两次，所有结果及校验码均与浏览器完全一致。

这证明失败局可以通过再次调用 `fight_getlevelbattledata` 直接换种子，后台无需等待 `fight_calcleveltime` 给出的整段战斗时间。2026-09-05 又完成了独立后台延迟结算：第 5903 关首局预测胜利，保留同一局等待 267 秒后提交 `fight_level`，服务器确认通过并进入第 5904 关；累计过关 1、模拟 1 局。当前实现仍保留 5 秒安全余量，并将加速开关默认关闭。

## 后台集成

`PushLevelBattleSimulator` 延迟加载并校验锁定资源，用单队列串行执行战斗，避免官方运行时的共享状态并发冲突。`PushLevelService` 增加可选加速循环；停止、任务替换和断线后都会检查运行代次，防止旧模拟提交 `fight_level`。接口、前端开关、状态和模拟局数显示已经接通，加速开关默认关闭。

首次运行或游戏版本更新后，先准备资源：

```powershell
node server/experiments/push-level/prepare-assets.mjs
```

本地资源保存在 Git 忽略的 `tmp/xki-analysis/`，不会随代码发布；生产环境默认保存在 `${DATA_DIR}/battle-assets/`。资源缺失、哈希不符或版本不符时，加速模式会拒绝启动，不会降级为未经核对的模拟。

已完成的本地验证包括：90 场人工输入矩阵、导出往返测试、多份真实输赢样本的浏览器与 Node 精确对照、胜局服务模拟冒烟测试、推关服务取消竞态测试、WebSocket 命令映射测试、前端生产构建、服务健康检查，以及独立后台连接中“预测胜利、等待正常时长、服务器成功结算”的完整闭环。原有普通推关流程仍走原分支。

现场测试还暴露了协议解码差异：BON 的 tag 8 同时表示普通对象和 Map，通用后端解码器无法区分；服务器还会省略默认值。模拟器因此在运行前以官方 `BattleData` 和队伍对象补齐默认值，并把战斗所需的队伍、属性、附魔及选项字段还原为 Map。浏览器完整样本、普通对象 Map 形态以及省略默认字段的真实协议形态均通过相同结果复算。

第 9559 关的复杂战斗还暴露了事件循环阻塞：单局计算需要约 20–27 秒，原先在主线程运行时会阻塞 5 秒心跳，导致所有账号同时收到 `conn timeout` 并以 1006 断线；个别战斗也会命中原 VM 的 20 秒上限。战斗运行时现已移入独立 Worker 线程，单局上限调整为 120 秒。现场复测先完成一局预测胜利并保持连接，随后连续完成两局预测失败并成功请求第二个随机局，全程没有再掉线。冒烟测试同时检查模拟期间主线程定时器持续运行。
